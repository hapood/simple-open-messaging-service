# SOMS C 端 UI 改造原则

状态：Draft v0.1  
范围：`web/` 及其 Tauri 内嵌运行形态  
首要验收平台：Android Tauri  
同步兼容平台：Windows/macOS Tauri、桌面浏览器、移动浏览器/PWA

## 1. 文档目的

本文档是 SOMS C 端界面全面改造的产品与设计基线，用来约束后续的信息架构、视觉设计、
组件实现和验收工作。

它不定义某一个页面的最终稿，也不改变现有业务能力。后续页面方案如果与本文档冲突，
应先更新本文档并记录原因，而不是在组件中形成新的局部规则。

## 2. 产品体验目标

SOMS 应呈现为一个轻量、可信、现代的即时通讯工具，而不是服务器功能的图形化入口。

用户不需要理解 Web、Tauri、SSE、推送通道、联邦协议等技术概念，也能完成以下核心任务：

1. 快速、安全地登录或配置所属服务器。
2. 找到联系人或会话，并理解是否有新消息。
3. 顺畅地阅读、发送和管理消息。
4. 在需要时找到个人资料、通知、设备和隐私相关设置。
5. 在弱网、权限拒绝或操作失败时，明确知道发生了什么以及下一步能做什么。

目标体验关键词：

- **清晰**：当前所在位置、可执行动作和系统状态一目了然。
- **克制**：减少无意义装饰、重复入口和过度动效。
- **亲和**：文案面向普通用户，视觉保持温和而非工具化。
- **可信**：登录、设备、网络和危险操作提供充分但不过度的解释。
- **连贯**：不同页面、平台和主题属于同一个产品，而不是多个参考产品的拼接。

## 3. 改造边界

### 3.1 本轮包含

- 导航和信息架构优化；
- 视觉语言、设计 token 与组件状态统一；
- 首页、会话列表、聊天、输入区、设置和认证体验优化；
- Compact、Medium、Expanded 三档响应式体验；
- 浅色、深色、中英文的一致性；
- Android 安全区、软键盘、横屏和触控体验；
- 桌面端鼠标、键盘和窗口缩放体验；
- 加载、空数据、失败、离线、权限和危险操作状态；
- 基础无障碍与视觉回归能力。

### 3.2 本轮默认不包含

- 重写消息虚拟列表、导航状态机或实时通信机制；
- 修改后端 API 和已有业务规则；
- 引入新的大型 UI 框架；
- 仅为了视觉效果引入高成本 3D、视频背景或复杂粒子动画；
- 在没有验证价值的情况下为每个平台维护独立页面实现。

如果界面目标确实需要业务或 API 变化，应作为独立需求记录和评审。

## 4. 平台优先级

### 4.1 Android Tauri：第一验收平台

所有核心链路首先以真实 Android 设备验收，而不是只以桌面浏览器模拟：

- 状态栏、刘海和底部手势区；
- 软键盘打开、关闭、切换输入法和横屏；
- 触控目标、长按、滑动和系统返回；
- 相机、麦克风、通知等权限；
- 弱网、断网、后台恢复和冷启动；
- 低端设备上的滚动、图片解码和 emoji 面板性能。

### 4.2 桌面 Tauri 与浏览器

桌面端不是移动界面的放大版本，需要支持：

- 鼠标 hover、右键和精确指针；
- 完整键盘导航与可见焦点；
- 窗口缩放、窄窗口和高分辨率屏幕；
- 主从栏布局、分栏宽度和快捷操作。

### 4.3 单一产品，不同呈现

各平台共享业务组件、token 和语义。布局和入口可随空间与输入方式变化，但功能命名、
状态含义和视觉身份必须一致。

## 5. 信息架构原则

### 5.1 以用户任务组织，而不是以技术模块组织

一级入口优先对应高频用户任务：

- 会话；
- 联系人与好友请求；
- 新建会话或群聊；
- 个人资料；
- 设置。

连接诊断、推送通道和日志上传等低频技术能力不应与外观、通知等日常设置平级展示，
应下沉到“帮助与诊断”或“高级设置”。

### 5.2 高频动作直接可见

移动端首页至少直接提供搜索、新建/添加和账户入口。不能把所有业务动作都隐藏在头像菜单中。

桌面端可以使用图标导航，但首次可理解性不能只依赖 hover tooltip；高频或有未处理状态的入口
应提供文字、角标或上下文说明。

### 5.3 一项任务只有一个主要入口

同一页面中应有一个明确的主操作。重复入口可以存在，但不能拥有同等视觉权重。

例如：

- 空会话页的主操作是“开始聊天”，辅助操作是“创建群聊”或“扫一扫”；
- 发送失败消息的主操作是“重试”，删除是次要操作；
- 服务器不可达的主操作是“重试”，重新配置是辅助操作。

### 5.4 渐进披露

默认界面只展示当前任务所需信息。危险操作、诊断信息和高级选项在用户主动进入后再呈现，
但不能以“完全隐藏”代替合理的入口设计。

## 6. 视觉语言原则

### 6.1 建立 SOMS 自有视觉身份

可以采用 Material 3 的交互与无障碍规范，也可以参考成熟 IM 的信息组织，但最终视觉不能表现为
Material、WhatsApp、Telegram 等产品风格的逐组件拼接。

初始方向：

- 保留现有蓝色作为唯一品牌主色；
- 使用中性、低噪声的页面和面板表面；
- 消息气泡颜色重新纳入品牌色体系，避免品牌蓝和 WhatsApp 绿竞争；
- 以色差和边框构建主要层级，阴影只用于真正浮起的元素；
- 使用统一的线性图标，禁止用系统 emoji 充当正式操作图标；
- 动效服务于空间关系、状态变化和操作确认。

### 6.2 内容优先

头像、会话名称、消息正文和操作反馈是视觉焦点。壁纸、渐变、装饰插画和大面积品牌元素不能
降低消息可读性。

### 6.3 层级数量受控

所有界面使用统一的表面层级：

1. App 背景；
2. 页面/面板表面；
3. 选中、悬停和弱强调表面；
4. 菜单、弹窗、浮层等 elevated 表面。

组件不得为追求“立体感”自行新增阴影等级。

### 6.4 字体和密度稳定

建立固定文字层级，不允许组件随意创建近似字号：

- 页面标题；
- 区域标题；
- 列表主标题；
- 正文；
- 辅助正文；
- 元数据与时间戳；
- 微型标签。

移动端保持舒适触控密度；桌面端可以提高信息密度，但不能通过缩小触控目标复用移动组件。

## 7. 设计 token 原则

`web/src/app/assets/_tokens.scss` 继续作为自有组件的 token 单一来源。

后续 token 至少覆盖：

- 品牌色及其容器色、按压色和对比文本色；
- 页面、表面、浮层和遮罩；
- 主文本、次文本、弱文本和禁用文本；
- 边框、分割线、hover、pressed、selected 和 focus；
- 成功、警告、危险和信息状态；
- 自己/他人消息及消息元数据；
- 字号、字重和行高；
- 间距、圆角、阴影和动效时长；
- 安全区、内容最大宽度和响应式尺寸。

规则：

- 业务组件使用语义 token，不直接依赖原始色值；
- 不使用未定义的 fallback token 掩盖缺失定义；
- 同一语义在浅色和深色主题下保持一致含义；
- Angular Material token 与 SOMS token 在全局主题层绑定，不在单个组件内零散覆盖；
- 硬编码色值只允许用于必须固定的媒体遮罩、白色图标或有注释说明的特殊效果。

## 8. 组件与交互原则

### 8.1 交互元素必须自解释

- 文字按钮直接说明动作；
- 图标按钮必须采用行业通用图标，并提供本地化 accessible name；
- 非常用或含义可能不明确的图标需要文字或上下文提示；
- 不把主要操作藏在没有提示的手势中；
- 长按录音等手势必须有首次提示和操作中反馈。

### 8.2 每个交互组件都有完整状态

至少覆盖：

- default；
- hover（适用平台）；
- pressed；
- focus-visible；
- selected/active；
- disabled；
- loading；
- error（适用组件）。

状态不能只通过透明度表达，也不能只依赖颜色区分。

### 8.3 触控与键盘基线

- 核心触控目标建议不小于 44×44 CSS px；
- 相邻危险与安全操作保留足够间距；
- 自定义可点击元素优先使用原生 `button`、`a` 或正确的 Material/CDK primitive；
- 所有操作可通过键盘到达并使用 Enter/Space 触发；
- 焦点环全局统一且不能被 `outline: none` 无替代地移除；
- 弹窗、抽屉和滑入页面正确管理进入焦点与关闭后的焦点返回。

### 8.4 动效基线

动效只承担以下职责：

- 说明页面或面板从哪里进入、返回到哪里；
- 确认按压、选择、发送和状态变化；
- 避免加载完成时的突然跳变。

所有非必要动效必须尊重 `prefers-reduced-motion`。相同类型过渡必须共享 duration 和 easing token。
不得因为装饰动效阻塞输入或延迟主要内容呈现。

## 9. 响应式原则

布局采用三档体验，而不是仅用“移动/桌面”一刀切：

| 模式 | 典型空间 | 核心结构 |
| --- | --- | --- |
| Compact | 手机、窄桌面窗口 | 单栏，聊天和详情全屏进入 |
| Medium | 平板、折叠屏、横屏手机 | 单栏增强或主从临时并列，侧面板以抽屉呈现 |
| Expanded | 桌面、大屏平板 | 导航、会话、聊天主从布局 |

具体断点由页面状态矩阵和实测决定，不以设备名称硬编码。

响应式不仅调整列数，还必须检查：

- 信息是否需要折叠；
- 操作是否转入菜单；
- 弹窗是否改为全屏页面或底部面板；
- 内容最大宽度是否合理；
- 横屏和软键盘同时出现时是否仍可操作。

## 10. 文案与反馈原则

### 10.1 面向普通用户

优先描述用户影响和下一步动作：

- 使用“正在重新连接”，而不是“SSE reconnecting”；
- 使用“服务器暂时无法访问”，而不是直接展示网络异常对象；
- 诊断详情可以在展开区域提供。

### 10.2 反馈就近、及时、可恢复

- 输入校验放在对应字段附近；
- 发送状态放在对应消息附近；
- 页面加载失败在内容区域提供重试；
- 全局 snackbar 只用于不属于特定区域的短暂反馈；
- 可恢复错误必须给出明确恢复动作；
- 破坏性操作说明对象和后果，并允许取消。

### 10.3 不以空白表示加载

所有异步页面必须定义 loading、empty、error 和 ready。骨架屏应匹配最终布局，避免加载完成跳动。

## 11. 无障碍与国际化基线

- 所有用户可见文案和辅助文本通过 Transloco 管理；
- 不在正式页面硬编码英文 `aria-label`、tooltip 或错误文案；
- 文本放大到 200% 时核心功能仍可使用；
- 不用颜色作为未读、失败、选中等状态的唯一表达；
- 正文、辅助文字、图标和交互状态满足合理对比度；
- 图片具备合适的替代文本，纯装饰图片明确隐藏于辅助技术；
- 动态错误、连接状态和发送状态使用适度的 live region，避免重复播报；
- 中文、英文长文本以及用户名、域名等不可控内容必须验证溢出和换行。

## 12. 性能原则

界面精细化不能以降低聊天流畅性为代价。

- 首屏不加载非必要的设置、编辑器和诊断页面代码；
- 长会话滚动和输入响应优先级高于装饰动画；
- emoji、媒体缩略图和头像需要关注内存占用与解码成本；
- 避免同时常驻大量不可见但仍参与布局或绘制的节点；
- 以真实低端 Android 设备验证冷启动、首次进入聊天、输入延迟和长列表滚动；
- 页面切换不应重复创建连接或消息内核。

## 13. 核心链路优先级

改造按用户价值而不是代码目录推进：

1. 打开 App → 登录/恢复会话；
2. 首页 → 搜索、添加或选择会话；
3. 进入聊天 → 阅读和发送消息；
4. 消息失败、断网和恢复；
5. 查看联系人/群资料；
6. 管理通知、设备和常用偏好；
7. 低频管理与诊断能力。

第一批实现聚焦第 2–4 项，形成可复用的列表、头部、消息和输入组件规范。

## 14. 完成定义

一个页面或组件只有同时满足以下条件才算完成：

- 业务功能和原有关键行为没有退化；
- Compact、Medium、Expanded 代表尺寸通过检查；
- Android Tauri 真实设备完成触控、软键盘、安全区和系统返回验证；
- 浅色、深色、中英文通过视觉检查；
- loading、empty、error、ready 及权限/离线状态有定义；
- 鼠标、触控和键盘均可完成核心操作；
- 图标、文案、间距、颜色和动效使用统一规范；
- 相关单元测试、构建和视觉基线通过；
- 没有新增无说明的硬编码颜色、字号、阴影或英文辅助文本。

## 15. 暂定决策与待确认项

以下作为后续方案的默认输入，可在视觉稿阶段调整：

### 暂定决策

- 保留蓝色品牌主色；
- 采用 Material 3 行为规范，但建立 SOMS 自有视觉；
- Android Tauri 为第一验收平台；
- 保持当前业务能力和导航状态机；
- 使用三档响应式体验；
- 优先改造首页、会话列表、聊天头部、消息区和输入区。

### 待后续产出验证

- 自己/他人消息气泡的最终色彩；
- 是否保留以及如何简化聊天壁纸；
- Medium 模式采用临时双栏还是增强单栏；
- 移动端新建入口使用独立按钮、FAB 还是顶部操作；
- 设置中的“高级/诊断”入口层级；
- 桌面左侧导航保留纯图标还是增加可展开文字模式。

## 16. 后续产出

1. 页面与状态验收矩阵；
2. 新版设计 token 草案与现有 token 迁移表；
3. 首页、会话列表和聊天页低保真结构方案；
4. 第一批核心链路实施计划；
5. 视觉回归、无障碍和真实设备验收方案。
