# Federation signing-key rotation and Health-driven discovery refresh

Status: proposed implementation design. The SOMFP wire contract remains defined by
[`spec/v1/transport-security.md`](../../spec/v1/transport-security.md) and
[`spec/v1/recognition.md`](../../spec/v1/recognition.md).

## Scope

This design covers the reference implementation's local signing-key lifecycle and
its peer-key cache refresh policy. It does not add an endpoint, change the
`/.well-known/somfp` JSON shape, change Recognize, or add fields to Health.

The pinned root key remains the durable federation identity. Signing keys are
shorter-lived online keys authorized by that root. Normal signing-key addition,
activation, expiration, and removal does not reset recognition, peer acceptance,
cursors, mirrors, or authorizations.

## Existing recognition lifecycle

Recognize is a bootstrap and acceptance-notification operation, not the normal
recovery operation for an already recognized peer:

- A locally recognized peer whose acceptance is not yet proven is `establishing`.
- The reconnect sweep retries Recognize only for `establishing` peers with
  `peerAcceptanceConfirmed = false`.
- A valid Recognize `recognized`, inbound valid Recognize, or Health `available`/`degraded`
  result proves peer acceptance. Once that fact is committed, Recognize retry
  stops.
- A recognized peer that loses current transport reachability is `degraded`.
  Its recovery path is periodic signed Health, not repeated Recognize.
- A positive Health result restores current reachability and may move the peer to
  `available`; Health `unavailable`, an HTTP failure, or a transport failure
  keeps a previously accepted peer `degraded`.

An inbound Recognize still fetches and validates the signer's current well-known
before accepting the request. An outbound Recognize still fetches the recipient's
well-known before preparing and signing the request. Key rotation does not change
these handshake semantics.

## Local signing-key lifecycle

The reference implementation stores local federation key material and signing
lifecycle state in PostgreSQL, not in `data/soms-s2s-key.json`. The old local key
file is not migrated, parsed, or used for compatibility; deployments adopting
this design generate fresh database-backed local key material when no database
identity exists. Database credentials and backups therefore protect federation
private keys.

The database must maintain exactly one signing key selected for new outbound
signatures at any instant and may maintain a published predecessor or successor
for verification overlap. The lifecycle is time-driven rather than selected by a
manually edited `active` flag:

1. Generate a successor and an authorized certificate under the unchanged root.
2. Publish the successor in local well-known while the predecessor remains
   current. Its `notBefore` is in the future or already current, as appropriate;
   it must be published before the first request signed with it.
3. When the implementation switches its outbound signer, atomically select the
   successor as the only key used for new outbound signatures. The successor
   must already satisfy `notBefore <= now < notAfter`, and its `notBefore` must
   be earlier than the planned switch by at least the configured clock-skew
   budget. The predecessor must remain valid beyond this switch.
4. After the switch, retain the predecessor as verification-only: keep it
   published through its advertised `notAfter`, but never select it for a new
   outbound signature.
5. After the predecessor's `notAfter`, stop publishing it and remove its private
   material according to the local retention policy.

The local implementation must never sign before `notBefore` or at/after
`notAfter`. It must atomically persist lifecycle changes in one database
transaction so a restart or concurrent scheduler run cannot select two active
keys or sign with a key outside its validity interval.

The implementation stores the root public/private key, signing public/private
keys, certificate validity intervals, `currentKeyId`, `plannedSwitchAt`, and
`plannedSuccessorKeyId` in database tables. These state fields are local only:
they are not well-known fields and do not change the federation wire shape. The
root private key is not used for ordinary HTTP request signing, but it is still
required to authorize each signing-key certificate published in well-known.

Existing installations generated by the older file-based implementation used
`<domain>/key-1` for the initial signing key. This design does not preserve that
local file state. Fresh database-backed identities should generate signing key
IDs as opaque names, such as `<domain>/k-<base64url-random>`, where the `KeyName`
satisfies the protocol grammar and is never reused under the same root. The
implementation must not derive key order, active status, or rotation
relationships from the key name.

Recommended initial timing defaults are:

- finite signing-key lifetime: 30 days;
- clock-skew budget: 10 minutes maximum relative UTC wall-clock difference
  between local and peer request-validation clocks;
- successor prepublication: 24 hours before the planned switch;
- post-switch predecessor retention: 24 hours;
- the planned switch is therefore halfway through the default two-sided
  overlap, but the implementation MUST calculate prepublication and
  post-switch grace independently rather than deriving the switch from a
  midpoint;
- minimum successor prepublication safety bound: at least the configured
  clock-skew budget plus expected peer well-known discovery, validation,
  scheduler, and network delay;
- minimum predecessor post-switch safety bound: at least the configured
  clock-skew budget plus the maximum HTTP signature lifetime, retry/delivery
  latency, expected peer discovery interval, and scheduler margin. The protocol
  recommendation is at least one hour and normally 24 hours or more for
  intermittently connected peers.

These are deployment defaults, not new wire fields. Certificate timestamps remain
the only interoperable timing data exposed to peers. The clock-skew budget is not
advertised to peers and must not be implemented as receiver-side certificate
validity grace; receivers still evaluate the exact half-open interval
`[notBefore, notAfter)`. If local clock-health monitoring cannot maintain the
configured budget, the implementation should suspend automatic switching and
rotation cleanup until the operator or clock source restores the assumption.

The implementation should add database schema for local key material and
rotation state, but it must not add compatibility code or data migration from the
old file-based key store. The existing `S2SKeyCache` table is sufficient for peer
certificate sets; no remote `activeKeyId`, `preferredKeyId`, or persisted
`nextRefreshAt` is required. Peer refresh deadlines are computed from cached
certificate rows when needed.

## Peer-key cache refresh

`S2SKeyCache` is authoritative for the locally cached peer certificate set within
a pinned identity namespace. Refreshing it replaces the complete set atomically;
it does not replace the pinned root.

The implementation has two discovery refresh triggers and one local diagnostic path:

1. **Inbound non-Health authentication key miss:** while validating an inbound
   signed request other than Health from a peer whose signer domain is already
   known in the applicable recognition context, a missing or locally expired
   `keyId` causes a rate-limited well-known fetch. The original request is then
   retried through the in-process validation path using the refreshed document.
   Bootstrap Recognize is the exception: its dedicated bootstrap path obtains
   and validates the signer's well-known before committing recognition, as
   defined by recognition.md. Inbound Health is intentionally excluded: it must
   not initiate well-known discovery while answering the query.
2. **Health overlap refresh:** after a successful outbound Health round trip,
   inspect the cached peer certificate set. Compute the continuous validity
   coverage provided by the whole set from the current time, including
   not-yet-active successors that overlap or abut the current coverage. If that
   coverage ends within the configured refresh window, schedule a proactive
   well-known refresh. This refresh is maintenance and must not turn an
   otherwise successful Health result into a failure.
3. **Outbound Health authentication failure:** an outbound Health response with
   `401 FEDERATION_BAD_SIGNATURE` means the recipient failed to authenticate the
   local signer. The requester marks an already accepted peer `degraded`, keeps
   its pin and acceptance evidence, and enters bounded retry/diagnostics. It
   must not assume that refreshing the recipient's well-known repairs the
   recipient's cache of the requester's key. The recipient's cache of the
   requester's signing keys is maintained by the recipient's outbound Health
   overlap refresh and other ordinary discovery refreshes, not by discovery
   during inbound Health authentication. The retry must be a
   newly constructed request with fresh `Date`, `created`, `expires`, and HTTP
   signature; the failed signed request is never replayed unchanged.

The implementation must not infer the remote active key from a Health response:
Health responses contain only `status`. The cache's validity intervals and the
request's `keyId` are the available triggers. During overlap, validation selects
exactly the certificate named by `keyId`; it does not try both certificates for
the same request. Key IDs must be parsed with the shared `KeyId` grammar and
matched as complete strings, not by `KeyName` alone.

Peer refresh scheduling is based on set coverage, not on a guessed remote active
key and not merely on the largest `notAfter`. After atomically replacing a
peer's cached certificate set, compute the continuous half-open coverage interval
starting at `now`:

1. Discard certificates with `notAfter <= now` for scheduling purposes.
2. Sort remaining intervals by `notBefore`.
3. Start coverage only with an interval satisfying `notBefore <= now < notAfter`.
   If none exists, the cache has no currently usable certificate and should be
   refreshed as soon as rate limits allow.
4. Extend coverage while the next interval starts at or before the current
   `coverageEnd`. Intervals that start after `coverageEnd` do not extend the
   current coverage, even if their `notAfter` is later.
5. Schedule proactive refresh at `coverageEnd - peerCertificateRefreshWindow`,
   subject to minimum refresh spacing, single-flight state, and rate limits.

For example, `[Jan 1, Jan 31)` plus `[Jan 31, Mar 1)` is continuous and covers
through Mar 1, while `[Jan 1, Jan 31)` plus `[Feb 1, Mar 1)` has a gap and covers
only through Jan 31 for refresh scheduling. Request validation remains independent
of this scheduling calculation: it uses the certificate whose full `keyId` equals
the request's `keyid` and validates that certificate's exact
`[notBefore, notAfter)` interval.

## Single-flight and ordinary HTTP scheduling

All well-known fetches use the existing ordinary S2S HTTP scheduler via
`DiscoveryService.acquireRequestSlot()`, the same scheduler used by Health,
Recognize, and ordinary signed S2S requests. Media range transfers retain their
separate media/download scheduler.

`DiscoveryService` should provide a per-domain (and, where needed, namespace)
single-flight refresh. Concurrent callers for the same pinned peer await one
refresh promise. The implementation must:

- install the in-flight promise before network I/O;
- replace the complete key set only after the document and root continuity have
  been validated;
- clear the in-flight entry on both success and failure;
- rate-limit repeated refreshes for one domain;
- avoid holding the Health scheduler slot while starting a follow-up refresh;
- treat proactive refresh failure as maintenance failure when the triggering
  Health request already succeeded.

A short negative cache for a key that remains unpublished after a successful
refresh may protect the public S2S surface from repeated arbitrary `keyId`
misses. It must not suppress a different domain or a later normal rotation
refresh.

## Error and lifecycle mapping

The distinction between certificate failure and discovery failure is preserved:

| Situation | Result | Local peer state |
|---|---|---|
| Well-known temporarily unavailable | Retryable `503 INTERNAL` on the common authentication path | retain pin; accepted peer is `degraded` |
| Peer certificate unpublished/expired/not authorized | `401 FEDERATION_BAD_SIGNATURE` on the common authentication path; not a Health status object | retain pin; accepted peer is `degraded` |
| Outbound Health receives `401 FEDERATION_BAD_SIGNATURE` | Recipient could not authenticate the local signer; this is not a Health status projection | retain pin and acceptance evidence; accepted peer is `degraded`; bounded diagnostics/retry |
| Root differs from pinned root | identity mismatch / fatal halt | `halted` |
| Positive Health `available` or `degraded` | acceptance + reachability evidence | `available` when all local gates hold |

A failed peer-key refresh never changes the pinned root. A normal signing-key
rotation under that root never starts Recognize again for a peer whose acceptance
is already confirmed.

## Required implementation tests

The implementation should cover at least:

- successor publication before the planned switch, with `notBefore` at least the
  configured clock-skew budget before that switch, and automatic selection of
  the successor at that local switch;
- predecessor acceptance throughout the overlap and removal only after
  `notAfter`;
- strict `[notBefore, notAfter)` validation without receiver-side clock-skew
  grace;
- restart recovery at each lifecycle boundary;
- concurrent non-Health key misses producing one well-known request per peer;
- inbound Health key misses failing on the common authentication path without
  initiating well-known discovery;
- outbound Health success scheduling an overlap refresh from the certificate
  set's continuous coverage end, not from a guessed active key or the maximum
  `notAfter`, and without changing the Health result;
- outbound Health `401 FEDERATION_BAD_SIGNATURE` marking an accepted peer
  degraded without replacing the pin or entering `halted`, and retrying only
  with newly constructed signature metadata after diagnostics;
- temporary well-known failure versus invalid/expired certificate error mapping;
- root mismatch halting without replacing the root pin;
- no Recognize retry for `available` or `degraded` peers after acceptance is
  confirmed.
